— 账号密码登录（辅助路径）—
四、账号密码登录怎么玩登录 PRD 功能块四
新增
给不方便用手机号快捷登录的供应商，留一条账号密码登录的路。
显示逻辑
页面上有：账号输入框（提示"请输入手机号"）、密码框（打码 + 能切换明文）、【登录】按钮、【忘记密码】。原型已还原
校验规则
① 账号或密码没填 → 按钮置灰点不了（原型为了好演示，改成能点 + 提示拦截）原型有差异
② 账号或密码错 → 红字【账号或密码错误】，不说具体哪个错（防人瞎猜密码）
③ 连错 5 次 → 锁 15 分钟，红字【错误次数过多，请 15 分钟后重试】，按钮置灰显示倒计时
交互逻辑
【忘记密码】→ 走手机验证码重置；重置好之后登录，后面的流程跟手机号登录一模一样（包括多个账号让用户挑）。
未覆盖
按钮置灰、错误锁定、忘记密码流程——原型里随便输什么都能登录。
四、这条路跟微信授权的关系登录 PRD 功能块四
数据源
账号是谁由账号密码说了算；手机号读后台档案里的注册手机号；微信那边只是悄悄拿个身份标识。
交互逻辑
这条路不弹微信授权面板（那个面板只给手机号快捷登录用）；登录成功后悄悄记下绑定关系，不弹任何窗。以后这个微信再进来，直接进主页，不用再输密码。原型已还原
显示逻辑
跟手机号登录进的是同一套账号，数据完全一样。区别只有一点：这条路进来的账号，微信昵称是空的（用户没填过）→ 进"我的"页会出引导条。原型已还原
研发硬约束
昵称是空的不许自动去拿、不许弹微信授权，必须用户自己动手填。
— 我的页 · 身份区 —
5.4 我的页身份区 · 两行结构身份绑定 PRD 5.4
新增
身份区分两行显示；加上微信昵称；能编辑的地方只有 ✎ 一处。
数据源
第一行（账号名称）← 后台供应商档案里的，只读；第二行（微信昵称）← 用户自己填的、存在绑定关系上。
显示逻辑
从上到下：供应商账号名称（第一行、主字）→ 微信昵称（第二行、次字）。原型已还原
显示逻辑
昵称没填 → 第二行显示橙色的 【微信昵称未设置，影响售后对接 · 点击完善 ✎】，整行都能点。原型已还原
显示逻辑
昵称多长都完整显示，不砍、不加省略号，太长就换行全露出来；换行时 ✎ 图标跟第一行文字对齐，不掉到最后一行。
交互逻辑
这页能编辑的只有 ✎ 一处。点击编辑按钮，弹出弹窗（这个弹窗长什么样、怎么开关，见下一张卡）。原型已还原
校验规则
第一行是账号名、第二行是微信昵称，各管各的不能合一起；账号名称只能看不能改。原型已还原
✎ 编辑弹窗 · 怎么开、长什么样、怎么关身份绑定 PRD 5.5
新增
专门讲"点 ✎ 之后弹出的那个编辑弹窗"——它是整个资料完善的唯一入口，之前缺一张专门说明的卡。
交互逻辑
怎么打开：一共三个口——① 昵称行右边的 ✎ 图标；② 昵称为空时第二行的橙色引导行（整行可点）；③ 顶部引导条的【去设置】。账号名称点了没反应（防手滑）。原型已还原
显示逻辑
弹窗长什么样：从屏幕下方升起的半屏弹层，背后页面变暗。内容从上到下：标题（没填过叫【完善微信昵称】，填过叫【更新微信昵称】）→ 一句说明 → 昵称输入框（右侧「使用微信昵称」）→ 字数计数 → 用途提示框 → 【保存】。原型已还原
交互逻辑
怎么关、关了会怎样：点【取消】或点旁边变暗的区域 → 弹窗关掉，填了一半的先留着不丢，下次打开还在；只有点【保存】才真正写进去。原型已还原
能力边界
这个弹窗不是微信授权弹窗——样子完全由我们自己定、自己画；全流程唯一的微信授权弹窗只有手机号那一次。
5.4 昵称展示与存储 · 全局规则身份绑定 PRD 4.1 / 5.4
存储规则
昵称按"微信 × 供应商账号"一条一条分开存——同一个微信绑两个账号，两个账号的昵称各是各的。
显示逻辑
C 端昵称没填就显示橙色引导行。原型已还原
校验规则
不能拿昵称查账号匙（会重名、会随时改）
异常与边界
昵称随便改，显示前把特殊字符转义掉防注入；显示多长都不砍；改昵称不影响绑定关系。
七、登录后顶部那条引导条登录 PRD 功能块七
新增
登录进来发现昵称是空的，页面顶部出一条不挡操作的引导条，提醒去填；以及它跟身份确认弹层的先后顺序。
数据源
当前账号的微信昵称是不是空的。
显示逻辑
空 → 顶部出引导条，可以关掉；填过 → 不出。引导条等页面加载完再出，不挡下面的操作。原型已还原
显示逻辑
文案定稿：【完善微信昵称，在售后时可以根据昵称@到你】，右侧【去设置】、最右【×】可关闭原型已还原
交互逻辑
点【去设置】→ 打开 ✎ 编辑弹窗；点关闭 → 本次不再弹，想填随时点昵称行的 ✎。原型已还原
异常与边界
如果"要确认身份"和"要填昵称"撞到一起，只能弹一个：先弹身份确认，引导条等它关了再说（v1.2 定稿）。
— 微信昵称填写层 —
5.5 弹窗里有什么身份绑定 PRD 5.5
新增
昵称可以从微信一键带入：点输入框，键盘上方冒出「使用微信昵称」，点一下就填进来；原来单独一条的用途提示框已撤掉，那句话并进了说明文案。
数据源
昵称靠用户自己填——点输入框，键盘上方冒出「使用微信昵称」，点一下就填进来，也可以手打。微信不会自动给我们，没有接口可读。
显示逻辑
从上到下：标题 → 说明文案 → 昵称输入框（右侧「使用微信昵称」）→ 字数计数 →【保存】，不再单独出现用途提示框。原型已还原
显示逻辑
标题两种：没填过【完善微信昵称】/ 填过【更新微信昵称】原型已还原
字数固定显示 【当前字数/30】（如 0/30），不显示「还能输几个」——两种口径不能混用原型已还原
显示逻辑
说明文案定稿（原用途提示框内容并入）：「用于处理售后时，在售后群内找到你【昵称要与售后群的昵称一致】。」
未覆盖
键盘上方那条"点击可一键填入"的引导文案没画——那块是微信渲染的，真机上才看得到。
5.5 填了之后会发生什么身份绑定 PRD 5.5
交互逻辑
只有点【保存】才真正提交；点到别处不会自动提交；点【取消】或点变暗区域关掉 → 什么都没发生，填了一半的下回还在。原型已还原
校验规则
① 昵称空白 → 拦下，红字【请输入微信昵称】，库不写、弹窗不关原型已还原
② 跟原来一模一样 → 提示 【昵称没有变化】，不算改过、不关弹窗原型已还原
③ 最多 30 个字（emoji 算 1 个），到顶就打不进去，不会偷偷砍掉
存储规则
保存成功 → 提示 【保存成功】，关弹窗、刷新"我的"页、记一条变更日志（旧值 / 新值 / 时间，只有后台能看）、顶部引导条跟着消失。原型已还原
存储规则
昵称单独提交，点【保存】才入库；昵称必须填，空白一律拦。
校验规则
昵称跟原来一样 → 提示 【昵称没有变化】，不算改过、不关弹窗；填了一半没保存就关弹窗 → 草稿留着。原型已还原
异常与边界
没有「填了再清空」这条路——系统不提供清空，空白一律拦。
接口
变更日志在 C 端没有任何入口，只有后台能查；客服走售后反查详情看历史昵称（接口 GET /internal/binding/nickname-log）。v1.2 定稿 反查的时候连改名前的旧昵称也要查得到——客户经常只记得旧昵称。
研发硬约束（不可协商）身份绑定 PRD 5.5
研发硬约束
① 昵称输入框必须是可以聚焦的 input type="nickname"，禁止 readonly / disabled——一旦只读，「使用微信昵称」整个废掉
② 键盘上方那条工具条是微信在真机上画的，我们改不了样式、也不能用代码替用户点；基础库要 2.21.2 以上，开发者工具里看不见，验收必须真机
③ 上线前《用户隐私保护指引》里昵称必须声明，没声明这个功能就悄悄失效
④ 这套东西失败时全都没声没响：没声明指引 / 输入框只读 / 基础库太老，都不报错但都不工作，联调要一条条排查
原型说明
原型里的微信填写面板是我们自己画的演示壳——真的长什么样、怎么弹由微信说了算；开发必须按上面四条来。
微信做不到的事 · 认识要统一身份绑定 PRD 5.5 / 答辩口径
能力边界
昵称只是「填一下」，不是「授权」——没有授权弹窗这一说，别再写「授权微信昵称」；微信也不提供读取接口、改名也不通知我们，用户改了这边毫无感知。
交互逻辑
昵称：点输入框 → 再点工具条，两步，一次点击拿不到昵称。
授权次数
从头到尾就一次授权弹窗——手机号面板，还必须用户自己点出来。昵称工具条不算授权。
研发硬约束
进小程序不会自动同步昵称。技术上做不到，需求和话术里都不许这么写。唯一更新路径：✎ → 编辑弹窗 → 点「使用微信昵称」→ 保存。少了「保存」就白弄。
