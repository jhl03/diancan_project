## 一、背景与目标

### 1.1 背景

报价规则列表页当前每条规则有「启用 / 修改 / 删除」三个按钮，状态在卡片右上角以只读标签展示。运营在调整供应商报价的可用性时，需要逐条点「启用」，无法同时管理多条，也无法快速停掉一批规则。

### 1.2 目标

| # | 目标 | 衡量方式 |
|---|---|---|
| 1 | 单条规则可一键开启 / 关闭报价 | 单条操作点击次数 ≤ 1 次（不含确认） |
| 2 | 多条规则可批量开启 / 关闭 | 支持勾选与按筛选范围操作 |
| 3 | 操作结果对用户完全透明 | 结果提示必须包含成功 / 跳过 / 失败三态数量与明细 |
| 4 | 不破坏存量逻辑 | 列表、搜索、筛选、新增、修改、删除、字段展示零改动 |

### 1.3 非目标（本期不做）

- 不做规则的定时生效 / 失效（定时报价）。
- 不做同商品规则冲突校验（业务已确认允许并存）。
- 不做报价规则的操作审计日志（见第七章开放问题）。
- 不改造「新增报价规则」入口与表单。

## 二、术语与字段口径

### 2.1 术语

| 术语 | 定义 |
|---|---|
| 开启报价 | 该规则参与报价，供应商可按此规则接单 |
| 关闭报价 | 该规则停止参与报价 |
| 混选 | 一次勾选中同时包含已开启与已禁用的规则 |
| 目标态 | 批量操作写入的最终状态值（开启=1 / 关闭=0），**不是状态翻转** |
| 已加载 | 当前列表已渲染出来的规则（受分页影响） |

### 2.2 字段口径（关键，避免实现歧义）

| 字段 | 口径 | 是否被开关操作影响 |
|---|---|---|
| 规则 | 规则编号，如「规则：2」 | 否 |
| 商品品牌 | 规则关联品牌 | 否 |
| 报价商品 | 规则关联商品，多个以「、」分隔 | 否 |
| 可出餐城市 | 规则生效城市范围 | 否 |
| **报价时间** | **新增这条报价规则的时间**，规则创建时写入一次，之后不变 | **否** |
| **更新时间** | 最近一次**实际发生变更**的时间 | **是** —— 仅实际操作成功的规则刷新；被跳过的规则不刷新 |
| 报价金额 | 该规则的单笔报价金额 | 否 |
| 出餐方式 | 人工 / 自动 | 否 |
| 供应商名称 | 规则归属供应商 | 否 |
| 状态标签 | 右上角只读展示：启用中（绿）/ 禁用（红） | 是（只读展示，不可点击） |

> 口径澄清：「报价时间」是存量字段，语义为规则创建时间，**本期不新增、不修改**。「更新时间」沿用存量字段语义，开关操作成功即视为一次变更。

### 2.3 业务规则（已确认）

1. **同一商品可同时存在于多条规则中，且允许同时开启。** 开关不做冲突校验，不会因开启一条而自动关闭另一条。供应商端会同时看到这几条报价，由业务侧自行区分优先级。
2. **关闭报价后，卡片不置灰**，字段保持可读、可修改（禁用 ≠ 失效，用户常需"先禁用再修改"）。

## 三、功能需求

### 3.1 单条：开启 / 关闭报价

**位置**：卡片底部按钮区，第一个按钮（原「启用」按钮的位置），顺序为 **[开启报价 / 关闭报价] → [修改] → [删除]**。

**形态**：文字按钮，不做 Switch。文案随当前状态反转，避免与「修改 / 删除」的按钮语言不一致。

| 当前状态 | 按钮文案 | 按钮样式 | 右上角状态标签（只读） |
|---|---|---|---|
| 已禁用 | 开启报价 | 绿框绿字 | 禁用（红） |
| 启用中 | 关闭报价 | 灰框灰字 | 启用中（绿） |

**交互流程**：

| 步骤 | 表现 |
|---|---|
| 1. 点击按钮 | 按钮文案变「处理中…」并进入禁用态（灰化、`pointer-events: none`），防止重复点击 |
| 2. 请求发出 | 静默请求，**不刷新列表、不重排卡片位置**（长列表跳动是体验事故） |
| 3. 成功 | 状态切换 → 按钮文案反转 → 右上角标签切换 → **刷新该卡片「更新时间」为当前时间** → Toast「已开启报价」/「已关闭报价」 |
| 4. 失败 | 按钮文案**回滚到点击前的原值**，状态不变、更新时间不变 → 红色 Toast「操作失败，请重试」 |

**约束**：

- **不做二次确认。** 开关是可逆、单条、低风险操作，加确认属于过度设计。
- 单条操作进行中，全局锁 `busy` 生效，期间其他单条点击不响应。
- 失败必须回滚 UI —— 不回滚是最常见的事故源头。

### 3.2 批量：勾选式批量开启 / 关闭

#### 3.2.1 入口与选择态

| 元素 | 默认态 | 选择态（批量管理） |
|---|---|---|
| 工具栏右侧 | 「批量管理」文字入口 | 「完成」+「选择全部 N 条」（仅当筛选结果数 > 已加载数时出现） |
| 工具栏左侧 | 「共 N 条报价规则」 | 「全选已加载 N 条」/「全选」+ 复选框 |
| 卡片 | 无勾选框，底部显示三个操作按钮 | 卡片左侧出现勾选框，**卡片底部三个按钮隐藏**（避免两套操作语义打架），整卡可点选 |
| 悬浮「+ 新增报价规则」 | 显示 | **隐藏** |
| 底部固定操作栏 | 隐藏 | 显示「已选 N 条（共 M 条）｜ 已开启 X · 已禁用 Y」+「批量开启」「批量关闭」 |

- 进入批量管理时**不弹 Toast**（界面变化本身已足够明确，避免多余打扰）。
- 「批量开启」「批量关闭」在已选 0 条时置灰不可点。
- 底部计数栏**必须带总数**：「已选 5 条（共 68 条）」——这是用户判断"我选多了没"的唯一依据。

#### 3.2.2 全选的三层范围（核心）

全选范围必须与用户认知边界一致，**默认只选"看得见"的**。

| 列表状态 | 全选覆盖范围 | 按钮文案 | 底栏计数 |
|---|---|---|---|
| 仅加载了首屏（如 8 / 68） | 仅当前已加载的规则 | 「全选已加载 8 条」 | 已选 8 条（共 68 条） |
| 已滑到底、全部加载完 | 当前筛选结果全部 | 「全选」 | 已选 68 条（共 68 条） |
| 点「选择全部 68 条」跨页 | 当前筛选结果全部（含未加载） | 「已全选 68 条」 | 已选 68 条（全部） |

**跨页选择是独立的一次显式动作**：

- 入口有两处：工具栏「选择全部 N 条」、底栏右侧「选择全部 N 条」，两处触发同一个确认弹窗。
- 确认弹窗文案：
  - 标题：**选择全部 68 条规则？**
  - 正文：包括当前未加载的 **60** 条规则，后续批量操作将同时影响它们。
  - 按钮：取消 / 确认选择
- 确认后才把范围扩到全库，并 Toast「已选中全部 68 条规则」。
- 全选复选框的选中判定：已加载项全部被选中即显示为选中态；再次点击取消全选。

#### 3.2.3 筛选与批量的关系

批量操作的范围**永远跟随当前筛选条件**，三层口径：

| 操作 | 实际作用范围 |
|---|---|
| 勾选后批量 | 勾选的这些（必然都在筛选结果内） |
| 全选 | 当前筛选结果中**已加载**的部分 |
| 选择全部 N 条 | 当前筛选结果**全部**（含未加载），N 为筛选后总数，**不是全库总数** |

确认弹窗与结果弹窗都必须写明当前范围，否则用户不知道 N 从哪来：

> 范围：当前筛选「麦当劳」（含未加载的 4 条）

范围文案优先级：有品牌筛选 → `当前筛选「品牌名」`；有关键词 → `当前搜索「关键词」`；无筛选 → `当前列表`。

### 3.3 混选处理（本期最关键规则）

**核心原则：批量开关写入的是「目标态」，不是「翻转态」。**

| 场景 | 处理方式 |
|---|---|
| 批量**开启**时，勾选项中有**已是开启**的 | 该条**跳过**，不重复写入 |
| 批量**关闭**时，勾选项中有**已是禁用**的 | 该条**跳过**，不重复写入 |
| 所选项**全部**已是目标态 | **不弹确认**，直接 Toast「所选规则均已是开启状态，无需操作」/「…均已是禁用状态，无需操作」 |

**为什么跳过而不是全量覆写**：

- 全量覆写会让"状态本就正确"的规则「更新时间」被无意义刷新，用户查看"最近变更时间"时信息失真。
- 跳过是幂等的：重复点同一个批量按钮，结果不产生差异。
- 全量覆写唯一的"好处"是结果数字整齐，但代价是污染时间字段，不值得。

**对称性要求**：开启与关闭两个方向必须完全对称，文案反向即可。

#### 3.3.1 二次确认弹窗（批量必弹）

弹窗标题**只写真实会改变的条数**（不是勾选总数）——用户确认前看到的数字必须是实际会被改动的数字。

| 项 | 批量开启 | 批量关闭 |
|---|---|---|
| 标题 | 将开启 **3** 条报价规则 | 将关闭 **3** 条报价规则 |
| 正文（有跳过） | 已选 5 条，其中 **2 条已是开启状态**，将跳过、不重复写入。 | 已选 5 条，其中 **2 条已是禁用状态**，将跳过、不重复写入。 |
| 正文（无跳过） | 已选 **5** 条规则，将批量开启报价。 | 已选 **5** 条规则，将批量关闭报价。 |
| 正文（范围行） | 范围：当前筛选「麦当劳」（含未加载的 4 条） | 同左 |
| 确认按钮 | 确认开启 | 确认关闭（危险色） |

### 3.4 批量操作结果提示

批量执行完成后用 **Toast** 反馈（评审定稿：不使用结果弹窗）：

| 场景 | 提示 |
|---|---|
| 执行完成且无失败 | Toast「**操作成功**」 |
| 存在失败项 | 红色 Toast「成功 N 条，失败 K 条」 |
| 所选全部已是目标态 | 不执行，直接 Toast「所选规则均已是开启/禁用状态，无需操作」（见 3.3） |

执行完成后：清空已选、自动退出批量管理模式、列表状态刷新。

> **变更记录（v1.1）**：v1.0 曾设计"结果弹窗"（三态数量 + 成功/跳过/失败明细 + 操作时间 + 重试失败项），评审定稿改为轻量 Toast「操作成功」。被跳过规则「更新时间」不刷新的口径不变（见 2.2）。

### 3.5 分页加载

| 项 | 规格 |
|---|---|
| 每页条数 | **10 条**（v1.0 为 8 条，v1.1 调整） |
| 触发方式 | 列表滚动到底部前 40px 自动触发 |
| 加载中 | 列表底部显示「⟳ 加载中…」 |
| 还有更多 | 底部显示「上拉加载更多（已加载 10 / 68）」 |
| 已到底 | 底部显示「没有更多了」 |

**分页与选择的联动**：

- 加载新一页时**已选项保留**，但**不自动勾选**新加载进来的项。
- 列表重新渲染时保留滚动位置，避免加载后跳回顶部。

### 3.6 边界规则清单

| # | 规则 | 原因 |
|---|---|---|
| 1 | 切换筛选 / 执行搜索时，**必须清空已选**并 Toast「筛选条件已变化，已清空选择」 | 否则会出现"筛了麦当劳选 10 条，切到霸王茶姬点批量，实际改的还是那 10 条"的错位 |
| 2 | 加载新一页时已选项保留，新加载项不自动勾选 | 避免用户未察觉的选区扩大 |
| 3 | 全选文案必须带数量（已加载数 / 总数） | 让用户知道选择边界 |
| 4 | 跨页选择必须先确认 | 操作范围超出认知范围，是最高风险动作 |
| 5 | 退出批量管理或执行完成后清空已选 | 避免残留选择被下一次操作误用 |
| 6 | 关闭报价后卡片不置灰 | 禁用 ≠ 失效，需支持"先禁用再修改" |
| 7 | 同商品多规则允许同时开启，不做冲突校验 | 业务已确认 |
| 8 | 操作进行中按钮置灰不可重复点击 | 防抖 |
| 9 | 不刷新整页、不重排卡片 | 避免长列表跳动 |

## 四、状态机

### 4.1 单条规则状态

```
        ┌──────────────┐  点击「开启报价」   ┌──────────────┐
        │              │ ────────────────> │              │
        │    已禁用     │     处理中(700ms)  │    启用中     │
        │              │ <──────────────── │              │
        └──────────────┘  点击「关闭报价」   └──────────────┘
               ▲                                    ▲
               │           请求失败：回滚原态          │
               └────────────────────────────────────┘
```

| 当前态 | 触发 | 中间态 | 成功 | 失败 |
|---|---|---|---|---|
| 已禁用 | 点「开启报价」 | 按钮「处理中…」置灰 | 启用中，按钮变「关闭报价」，刷新更新时间，Toast「已开启报价」 | 回原态，红色 Toast「操作失败，请重试」 |
| 启用中 | 点「关闭报价」 | 同上 | 已禁用，按钮变「开启报价」，刷新更新时间，Toast「已关闭报价」 | 同上 |

### 4.2 列表管理模式

| 模式 | 进入 | 退出 |
|---|---|---|
| 浏览模式 | 默认 | 点「批量管理」进入选择态 |
| 选择态 | 点「批量管理」 | 点「完成」/ 批量执行完成 → 清空已选并回到浏览模式 |

### 4.3 批量操作分支

```
点「批量开启 / 批量关闭」
      │
      ├─ 已选 0 条 → 按钮置灰，不可点
      │
      └─ 已选 N 条
            │
            ├─ 全部已是目标态 → Toast「所选规则均已是X状态，无需操作」（不弹确认）
            │
            └─ 存在待变更项
                  │
                  └─ 弹确认（标题为真实变更条数）
                        │
                        ├─ 取消 → 停留在选择态，已选保留
                        │
                        └─ 确认 → 执行
                              │
                              ├─ 全部成功 → 结果弹窗（成功N/跳过M/失败0）
                              ├─ 部分失败 → 结果弹窗 + 「重试失败项」
                              └─ 执行后：清空已选、退出选择态
```

## 五、接口契约

### 5.1 单条切换状态

```
POST /api/quote-rule/status
Content-Type: application/json

{ "ruleId": 1, "status": 1 }        // 1=开启报价  0=关闭报价
```

**响应**

```json
{
  "code": 0,
  "data": {
    "ruleId": 1,
    "status": 1,
    "updateTime": "2026-09-24 11:02:33"
  }
}
```

- 返回的 `updateTime` 直接回填卡片「更新时间」，保证"开关也是一次变更"逻辑自洽。
- 失败：`{ "code": 50001, "msg": "操作失败，请重试" }`，前端回滚 UI。

### 5.2 批量切换（按勾选 id）

```
POST /api/quote-rule/status
{
  "ruleIds": [1, 2, 9],
  "status": 1,
  "skipSameStatus": true            // 跳过已是目标态的规则，不重复写入
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "changedCount": 3,
    "skippedCount": 2,
    "failList": [ { "id": 19, "title": "规则：64", "reason": "操作超时" } ],
    "updateTime": "2026-09-24 11:02:33"
  }
}
```

### 5.3 批量切换（跨页全选，传筛选条件）

```
POST /api/quote-rule/status
{
  "filter": { "brand": "麦当劳", "city": "", "keyword": "" },
  "status": 0,
  "skipSameStatus": true
}
```

**响应**：同上，额外返回 `affectedCount`（实际匹配的规则总数），前端据此提示「已关闭 68 条报价规则」。

> 为什么不传 id 列表：几十上百个 id 传前端既冗余又易错；且筛选与执行之间若产生新增数据，以筛选条件为准语义更清晰。

### 5.4 列表查询（存量接口，仅确认分页参数）

```
GET /api/quote-rule/list?page=1&pageSize=8&brand=&keyword=
```

需返回总数 `total`，前端才能渲染「已加载 8 / 68」与三层全选文案。

## 六、埋点建议

| 事件 | 关键参数 | 用途 |
|---|---|---|
| 单条开关点击 | ruleId、目标状态、结果（成功/失败） | 评估单条操作频率与失败率 |
| 批量管理进入 | 当前筛选条件、列表总数 | 评估批量功能使用广度 |
| 全选范围使用 | 范围类型（已加载 / 全部加载 / 跨页） | 判断"跨页全选"是否真被需要 |
| 批量执行 | 勾选数、真实变更数、跳过数、失败数 | 评估混选场景占比 |

**重点观测**：跨页全选的使用频次。若长期为 0，建议下线该能力，只保留「全选已加载」，认知负担与误操作风险都更低。

## 八、验收标准

| # | 用例 | 预期 |
|---|---|---|
| 1 | 点击「规则：2」的「开启报价」 | 按钮变「处理中…」→ 状态标签变「启用中」→ 按钮变「关闭报价」→ 更新时间刷新为当前时间 → Toast「已开启报价」 |
| 2 | 模拟接口失败后点击单条开关 | 按钮文案回到原值、状态不变、更新时间不变、红色 Toast「操作失败，请重试」 |
| 3 | 进入批量管理，勾选 5 条（其中 2 条已开启），点「批量开启」 | 弹窗标题为「将开启 **3** 条报价规则」，正文写明「其中 2 条已是开启状态，将跳过」 |
| 4 | 承接用例 3 确认后 | Toast「操作成功」；已选清空、退出批量管理；3 条状态变更、「更新时间」刷新，被跳过的 2 条「更新时间」不变 |
| 5 | 勾选 5 条全部已开启，点「批量开启」 | 不弹确认，直接 Toast「所选规则均已是开启状态，无需操作」 |
| 6 | 首屏加载 10 条时查看全选文案 | 显示「全选已加载 10 条」，底栏显示「已选 10 条（共 68 条）」 |
| 7 | 点「选择全部 68 条」 | 弹确认「包括当前未加载的 60 条规则…」，确认后计数变「已选 68 条（全部）」 |
| 8 | 选择态下切换品牌筛选 | 已选立即清空，Toast「筛选条件已变化，已清空选择」 |
| 9 | 上拉加载第二页 | 已选项保留，新加载项未被自动勾选，滚动位置不跳回顶部 |
| 10 | 批量执行中出现 1 条失败 | 红色 Toast「成功 N 条，失败 1 条」，成功项状态已变更、失败项保持原态 |
| 11 | 开启同一商品的多条规则 | 两条均可同时开启，无冲突拦截、无自动禁用 |
| 12 | 关闭报价后查看卡片 | 卡片不置灰，字段可读，修改 / 删除仍可用 |
| 13 | 点击确认弹窗中的「确认开启 / 确认关闭」 | 执行成功后 Toast 提示「操作成功」 |
